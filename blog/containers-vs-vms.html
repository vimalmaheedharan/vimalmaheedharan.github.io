Containers Didn't Kill the VM.
They Just Moved In Next Door.

Two different isolation boundaries get sold as the same idea with different packaging. They aren't. Here's the actual line between a container and a virtual machine — drawn with real numbers, not vibes.

Vimal Maheedharan9 min readInfrastructure / SRE
FIG. 01

The sentence that gets everyone in trouble

Somewhere along the way, "a container is just a lightweight VM" became the default explanation, and it's the kind of simplification that's close enough to sound right and wrong enough to cause an incident. A container isn't a smaller virtual machine. It's not virtualizing hardware at all. It's a regular process on the host, wearing a very convincing disguise — its own filesystem, its own hostname, its own process tree — built entirely out of features the Linux kernel already had.

A VM, meanwhile, is doing something categorically different: emulating an entire computer, convincingly enough that a full, independent operating system boots inside it and never has to know it's a guest.

Same goal — run this workload without it stepping on that one — answered at two completely different layers of the stack. That gap is where the interesting engineering, and the interesting failure modes, live.

The hypervisor's job is to lie to the guest OS about the hardware so convincingly that the guest never questions it. Each VM gets what looks like its own CPU, RAM, disk, and NIC — and its own kernel to manage them, which is why you can run Windows on a Linux host or an old kernel next to a new one on the same box.

The container runtime isn't emulating anything. There's one kernel, shared by the host and every container on it. What makes a container feel like its own machine is that the kernel has been asked, politely but firmly, to hide most of itself from each process group.

FIG. 03

The two primitives doing all the work

Everything a container "is" comes down to two kernel features, both older than Docker by a decade. Namespaces control what a process can see. cgroups control what it can use.

PIDIts own process tree — PID 1 inside is some other number outside.
NETIts own network stack: interfaces, routes, ports.
MNTIts own filesystem mount tree — the illusion of a fresh root.
UTSIts own hostname and domain name.
IPCIts own message queues, semaphores, shared memory.
USERIts own UID/GID mapping — root inside, nobody outside.

cgroups (v2, in current kernels) sit alongside namespaces and cap what a process group can consume — CPU shares, memory ceilings, I/O bandwidth, PIDs count — and account for it, which is also how docker stats and every Kubernetes resource limit actually gets enforced under the hood.

Neither of these is virtualization. They're visibility and accounting controls, applied to processes that are, underneath it all, ordinary residents of the host kernel. That distinction is the whole ballgame for what comes next.

None of this makes containers "worse." It makes them a different trade: you gave up the hardware-level wall in exchange for startup times and density that let a single node run a fleet where a VM-only design would run a handful. For a homogeneous stack of trusted, first-party services, that trade is usually correct. For a kernel-exploit-shaped worst case, it's the whole reason the isolation conversation exists at all.

Where this actually bites: the classic incident isn't a container "escaping" through some exotic zero-day. It's a team that assumed container boundaries carry VM-grade guarantees, ran genuinely untrusted or multi-tenant code with default settings, and treated the shared kernel as an implementation detail instead of the actual trust boundary it is.
FIG. 05

The gap in between: microVMs

The industry noticed this trade-off too, and spent the last several years building a third category to close it. Firecracker — the VMM AWS built for Lambda and Fargate — boots a minimal virtual machine with its own kernel in as little as ~125ms, using under 5MiB of memory overhead per instance, by emulating only about five devices instead of a full PC. That's hypervisor-grade isolation running at container-adjacent speed and density — close enough that AWS puts every single Lambda invocation, across trillions of executions a month, inside its own microVM.

Kata Containers and gVisor attack the same gap from the Kubernetes side: they let a pod look and behave like a normal container to the orchestrator, while actually running inside a lightweight VM or an intercepted, sandboxed syscall layer underneath — for exactly the workloads (multi-tenant SaaS, CI runners executing someone else's code, anything untrusted) where "shares a kernel with the rest of the node" is not an acceptable answer.

This is also the detail that quietly resolves the "containers vs. VMs" framing as a false choice: on every major cloud, a Kubernetes node is a VM, containers run inside it, and increasingly those containers are individually wrapped in a microVM for anything that touches another tenant. The stack isn't container or VM. It's usually both, nested, with the boundary drawn wherever the workload's trust level actually requires it.

FIG. 06

Choosing the boundary you actually need

Container

Your own services, a shared trust domain, a single kernel version you control. This is the default for microservices, internal APIs, CI build steps, and most of what runs behind a Kubernetes Service.

Full VM

You need a different OS or kernel than the host, hard regulatory or multi-tenant isolation between customers, or you're running something you genuinely don't trust and don't have a microVM layer available.

MicroVM / sandboxed runtime

You want container-shaped density and speed but the workload is untrusted or multi-tenant — serverless functions, third-party plugin execution, CI jobs running arbitrary customer code. Firecracker, Kata, or gVisor instead of a bare container.

The honest version of the pitch isn't "containers replaced VMs." It's that containers solved a packaging and density problem the VM was never built to solve cheaply, and VMs still solve an isolation problem containers were never built to solve at all. Most production systems today need both, at the same time, at different layers of the same box — which is exactly why the two haven't been competing for a while now. They've been coexisting, quietly, under names most people never bother to look up.
